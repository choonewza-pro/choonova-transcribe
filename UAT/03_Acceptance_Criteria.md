# Acceptance Criteria (เกณฑ์การยอมรับ)
**Project:** ChooNova Transcribe
**Version:** 1.0

เกณฑ์การยอมรับนี้ใช้เป็นมาตรฐานในการตัดสินว่าระบบหรือฟีเจอร์นั้นๆ "ผ่าน" การทดสอบและพร้อมสำหรับนำไปใช้งานจริง (Production)

---

## 1. เกณฑ์การยอมรับระดับฟีเจอร์ (Feature-level Acceptance Criteria)

### 1.1 การถอดเสียงแบบไฟล์ (Batch Transcription)
*   **AC1.1.1:** ระบบต้องสามารถรับไฟล์นามสกุลเสียงและวิดีโอมาตรฐาน (เช่น .mp3, .wav, .mp4, .m4a) ได้โดยไม่เกิดข้อผิดพลาด
*   **AC1.1.2:** ความแม่นยำในการถอดเสียงภาษาไทย (Typhoon ASR) ต้องอยู่ในระดับที่อ่านรู้เรื่อง เข้าใจความหมายของประโยคได้มากกว่า 85-90% (ขึ้นอยู่กับคุณภาพของไฟล์เสียงต้นฉบับ)
*   **AC1.1.3:** ระบบจะต้องแสดงข้อความผลลัพธ์บนหน้า Web UI ได้อย่างสมบูรณ์ และมีปุ่มให้สามารถคัดลอก (Copy) หรือดาวน์โหลดข้อความได้
*   **AC1.1.4:** กรณีที่ไฟล์มีความยาวมาก (เช่น เกิน 30 นาที) ระบบต้องประมวลผลได้จนจบโดยไม่เกิดอาการค้าง (Out of Memory) และคืนผลลัพธ์ได้ถูกต้อง

### 1.2 การถอดเสียงแบบเรียลไทม์ (Real-time Transcription)
*   **AC1.2.1:** เมื่อเปิดใช้งานไมโครโฟนผ่าน Web UI ระบบจะต้องจับเสียงและแสดงข้อความตอบกลับมาภายในเวลาไม่เกิน 1-2 วินาที (Low Latency)
*   **AC1.2.2:** เมื่อหยุดพูด ระบบต้องจัดกลุ่มประโยคให้ถูกต้องตามหลักภาษา

### 1.3 ความปลอดภัย (Security & Authentication)
*   **AC1.3.1:** การเรียกใช้ API `/v1/transcription` หรือ `/v1/settings` หากไม่แนบ Header `x-api-key` ที่ถูกต้อง ระบบต้องปฏิเสธการเข้าถึงและตอบกลับด้วย HTTP Status `401 Unauthorized` หรือ `403 Forbidden`
*   **AC1.3.2:** หน้า Web UI (Dashboard) สามารถเข้าถึงได้โดยไม่ต้องใช้ `x-api-key`

### 1.4 การจัดการโมเดลและทรัพยากร (Model VRAM Management)
*   **AC1.4.1:** เมื่อปรับการตั้งค่าโหมดของโมเดลเป็น `idle` และตั้งเวลา Timeout ไว้ที่ X วินาที หากไม่มีการเรียกใช้งานระบบนานเกิน X วินาที โมเดลจะต้องถูกถอดออกจาก VRAM อัตโนมัติ (ตรวจสอบได้จาก VRAM Usage บน GPU)
*   **AC1.4.2:** หลังจากการ unload โมเดลไปแล้ว หากมีผู้เรียกใช้งานระบบอีกครั้ง ระบบจะต้องสามารถโหลดโมเดลกลับมาใช้งานได้ใหม่โดยอัตโนมัติ (แม้จะใช้เวลาในการตอบสนองคำขอแรกนานขึ้นเล็กน้อย)

### 1.5 ความยืดหยุ่นและการกู้คืนจากข้อผิดพลาด (Resilience)
*   **AC1.5.1:** ในกรณีที่ Worker ภายใน (Subprocess) เกิดการแครช (Crash) หรือขัดข้องจาก GPU (CUDA Error) ตัว Watchdog ของระบบจะต้องสามารถตรวจจับ ยุติงานนั้น และเริ่ม Worker ใหม่ได้โดยไม่ทำให้ระบบหลักล่ม (Main API ยังทำงานต่อได้)

## 2. เกณฑ์การยอมรับระดับระบบ (System-level Acceptance Criteria)
*   **ความเสถียร (Stability):** ระบบสามารถเปิดใช้งานต่อเนื่อง (Uptime) ในรูปแบบ Docker Compose ได้โดยไม่มีอาการ Memory Leak ที่ส่งผลให้คอนเทนเนอร์หยุดทำงาน
*   **ประสิทธิภาพ (Performance):** การตอบสนองของหน้า Web UI ในการคลิกเมนูต่างๆ ต้องรวดเร็ว ไม่มีอาการหน่วงจนรบกวนประสบการณ์ใช้งาน
*   **สภาพแวดล้อม (Environment):** ระบบสามารถรันได้ทั้งบนโหมด GPU (ใช้งาน CUDA) และ CPU (ในกรณีเครื่องไม่มี GPU) ตามที่กำหนดไว้ในคู่มือการติดตั้ง
